좋다. 이 구조는 다음 한 문장으로 시작하면 된다.

\[
\boxed{
\text{2N Segment Tree}
=
\text{leaf를 }[n,2n)\text{에 직접 놓고, query 경계만 올려가며 처리하는 bottom-up tree}
}
\]

핵심은 **각 노드의 구간 의미보다 query invariant를 신뢰한다**는 것이다.

---

## 1. 기본 정의

배열을

\[
a_0,a_1,\dots,a_{n-1}
\]

라 하고, 결합 연산을

\[
\circ
\]

라 하자.

필요한 조건은 결합법칙이다.

\[
(a\circ b)\circ c=a\circ(b\circ c)
\]

항등원 \(e\)도 두면 편하다.

\[
e\circ x=x\circ e=x
\]

즉 보통 monoid를 생각하면 된다.

---

## 2. Layout

padding 없이 곧바로

\[
\boxed{t[n+i]=a_i}
\]

로 놓는다.

따라서 leaf는

\[
[n,2n)
\]

이다.

부모는 평범하게

\[
\boxed{
t[i]=t[2i]\circ t[2i+1]
}
\]

로 만든다.

```cpp
vector<long long> t(2 * n);

for (int i = 0; i < n; i++)
    t[n + i] = a[i];

for (int i = n - 1; i >= 1; i--)
    t[i] = t[2*i] + t[2*i+1];
```

Build:

\[
\boxed{O(n)}
\]

Memory:

\[
\boxed{2n}
\]

---

# 3. \(n\neq2^k\)이면 이상한 일이 생긴다

예를 들어 \(n=5\).

\[
t_5=a_0,\quad
t_6=a_1,\quad
t_7=a_2,\quad
t_8=a_3,\quad
t_9=a_4
\]

그러면

\[
t_4=a_3\circ a_4
\]

\[
t_3=a_1\circ a_2
\]

그런데

\[
\boxed{
t_2=(a_3\circ a_4)\circ a_0
}
\]

이다.

즉 `t[2]`는 원래 배열의 연속구간이 아니다.

트리는:

```text
                 1
              /     \
             2       3
           /  \     / \
          4   a0   a1 a2
         / \
        a3 a4
```

이다.

따라서 \(n\neq2^k\)이면 일반적으로

\[
\boxed{
\text{node }i
\not\leftrightarrow
\text{원래 배열의 연속구간}
}
\]

이다.

심지어 비가환 연산이면 `t[1]`도 배열 전체의 올바른 순서가 아니다.

\[
t_1
=
a_3\circ a_4\circ a_0\circ a_1\circ a_2
\]

따라서

\[
\boxed{\text{임의의 internal node를 직접 해석하면 안 된다.}}
\]

---

# 4. 그런데 query는 정확히 된다

구간

\[
[L,R)
\]

을 구한다고 하자.

처음 경계를 leaf 위치로 옮긴다.

\[
l=L+n,\qquad r=R+n
\]

그리고:

```cpp
T left = e;
T right = e;

while (l < r) {
    if (l & 1)
        left = left ◦ t[l++];

    if (r & 1)
        right = t[--r] ◦ right;

    l >>= 1;
    r >>= 1;
}

return left ◦ right;
```

C++ 식으로 쓰면:

```cpp
long long query(int l, int r) {
    long long left = 0;
    long long right = 0;

    l += n;
    r += n;

    while (l < r) {
        if (l & 1)
            left += t[l++];

        if (r & 1)
            right = t[--r] + right;

        l >>= 1;
        r >>= 1;
    }

    return left + right;
}
```

---

# 5. 왜 `l & 1`인가

heap indexing에서는

\[
2k=\text{left child},
\qquad
2k+1=\text{right child}
\]

이다.

따라서

\[
l\&1=1
\]

이면 \(l\)은 오른쪽 자식이다.

```text
       parent
       /    \
    l-1      l
             ^
```

그런데 현재 query는 \(l\)부터 시작하므로 `l-1`은 범위 밖이다.

따라서 \(l\)을 부모로 올리면

\[
\text{범위 밖 sibling}
\]

과 섞인다.

그래서 **올라가기 직전에** 떼어낸다.

\[
\boxed{
l\text{ odd}
\Rightarrow
\text{take}(l),\quad l\leftarrow l+1
}
\]

오른쪽도 대칭이다.

\(r\)은 exclusive boundary이므로 \(r\)이 odd이면

\[
r-1
\]

이 왼쪽 자식이고 그 오른쪽 sibling은 query 밖이다.

따라서

\[
\boxed{
r\text{ odd}
\Rightarrow
r\leftarrow r-1,\quad \text{take}(r)
}
\]

한다.

---

# 6. 왜 그다음 `/2`가 정확한가

두 boundary 처리를 끝내면 반드시

\[
l=2p,\qquad r=2q
\]

이다.

남은 frontier는

\[
2p,2p+1,
2p+2,2p+3,
\dots,
2q-2,2q-1
\]

이다.

즉 전부 sibling pair다.

따라서

\[
(2p,2p+1)\to p
\]

\[
(2p+2,2p+3)\to p+1
\]

등으로 정확히 접을 수 있다.

결국

\[
\boxed{
[2p,2q)\longrightarrow[p,q)
}
\]

이므로

\[
l\gets l/2,\qquad r\gets r/2
\]

가 정확하다.

---

# 7. Query의 진짜 invariant

원래 query를 \(Q=[L,R)\)라 하자.

매 순간

\[
\boxed{
Q=
\text{left에서 이미 처리한 부분}
\;\sqcup\;
\text{현재 frontier}
\;\sqcup\;
\text{right에서 이미 처리한 부분}
}
\]

이다.

각 iteration은:

\[
\boxed{
\text{boundary prune}
\rightarrow
\text{sibling contraction}
}
\]

이다.

즉:

\[
\boxed{
\text{prune before merge}
}
\]

가 correctness의 핵심이다.

\(2N\) tree 내부에는 `a3,a4,a0`처럼 이상하게 섞인 node가 존재할 수 있다.

하지만 query가 그런 잘못된 merge를 사용하려는 **바로 직전 단계에서 boundary parity가 깨진다.**

그 순간 `&1`이 그것을 떼어낸다.

따라서:

\[
\boxed{
\text{bad merge가 query 결과에 들어오기 전에 반드시 prune된다.}
}
\]

이게 arbitrary-\(n\)에서도 동작하는 핵심 증명이다.

---

# 8. `&1`의 더 깊은 의미

단순 홀짝 검사가 아니다.

\[
\boxed{
\text{현재 scale에서 boundary가 sibling block에 정렬되어 있는가?}
}
\]

를 검사한다.

그리고

```cpp
l >>= 1;
```

은 binary digit 하나를 버리면서 한 scale 위로 올라가는 것이다.

따라서 query는 사실:

\[
\boxed{
\text{각 binary scale에서 boundary alignment를 검사하면서}
[l,r)\text{를 canonical blocks로 분해}
}
\]

하는 알고리즘이다.

# 9. Point update

\(a_p\leftarrow x\)라면:

\[
i=p+n
\]

에서 leaf를 바꾸고 조상들을 복구한다.

```cpp
void update(int p, long long x) {
    p += n;
    t[p] = x;

    while (p > 1) {
        p >>= 1;
        t[p] = t[2*p] + t[2*p+1];
    }
}
```

복잡도:

\[
\boxed{O(\log n)}
\]

---

# 10. 비가환 연산도 가능하다

중요하다.

\[
a\circ b\neq b\circ a
\]

여도 결합법칙만 있으면 query 가능하다.

그래서 양쪽 accumulator를 따로 둔다.

\[
L\leftarrow L\circ t[l]
\]

하지만 오른쪽은

\[
R\leftarrow t[r]\circ R
\]

이어야 한다.

즉:

```cpp
if (l & 1)
    left = op(left, t[l++]);

if (r & 1)
    right = op(t[--r], right);
```

마지막에

\[
\boxed{op(left,right)}
\]

한다.

이 순서를 바꾸면 문자열 concat, matrix multiplication 같은 연산에서 틀린다.

---

# 11. 무엇이 장점인가

\[
\boxed{
\begin{aligned}
\text{memory} &: 2n\\
\text{build} &: O(n)\\
\text{point update} &: O(\log n)\\
\text{range query} &: O(\log n)\\
\text{recursion} &: \text{없음}\\
\text{padding} &: \text{없음}
\end{aligned}
}
\]

그래서 단순한

\[
\boxed{
\text{point update + associative range query}
}
\]

에는 매우 강하다.

---

# 12. 무엇을 잃는가

가장 큰 대가는

\[
\boxed{
node\leftrightarrow[l,r)
}
\]

라는 geometry를 잃는 것이다.

그래서 다음은 덜 자연스럽다.

- lazy propagation
- persistent segment tree
- dynamic huge interval
- root에서 내려가는 `k-th`
- node 길이가 필요한 연산
- 복잡한 구조적 탐색

가능한 것도 많지만, `4n recursive`나 `next_pow2`가 훨씬 자연스러운 경우가 많다.

---

# 13. 다른 두 방식과 비교

\[
\boxed{
\begin{array}{c|c}
\text{구현} & \text{구간 geometry의 위치}\\
\hline
next\_pow2 & \text{regularized array layout}\\
4n\ recursive & (node,l,r)\text{ recursion state}\\
2n\ iterative & \text{query boundaries }(l,r)
\end{array}
}
\]

즉 `2N`의 가장 독특한 점은:

\[
\boxed{
\text{node geometry를 버리고 boundary invariant만 보존한다}
}
\]

는 것이다.

---

# 14. 이름

보통:

\[
\boxed{\text{bottom-up iterative segment tree}}
\]

라고 부르는 것이 가장 안전하다.

설명적으로는:

- `2N segment tree`
- `2N layout`
- non-recursive segment tree

등도 쓴다.

중국 PS 문화에서는 `ZKW segment tree`라는 이름도 보인다.

---

## 최종 압축

2N Segment Tree의 본질은 이것이다.

\[
\boxed{
\begin{aligned}
&t[n+i]=a_i\\
&t[i]=t[2i]\circ t[2i+1]\\[1mm]
&\text{query:}\\
&\quad \text{prune misaligned boundaries}\\
&\quad \text{contract aligned sibling pairs}\\
&\quad \text{repeat}
\end{aligned}
}
\]

그리고 correctness의 핵심은:

\[
\boxed{
\text{잘못된 sibling과 merge될 최초의 순간에는
반드시 boundary parity가 그것을 탐지한다.}
}
\]

그래서 **트리 자체는 다소 기괴해도 query는 정확하다.**
